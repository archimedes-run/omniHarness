## What was built, by requirement

**The working loop (FR-050 to FR-062)**
- FR-050: `write_todos` is bound in every mode (`_create_todo_list_middleware` no longer gated on `is_plan_mode`).
- FR-051/052: the checklist's first item is "Done when: …" (tool text, todo system block, prompt). The todo gate (TodoMiddleware) now sends the lead back **once per turn** (it was twice per thread, and a thread that used its two never reminded again) when it finishes with unticked items and no "Not verified" list; an honest stop with a "Not verified" list, a forced loop stop, or a stop at a pending card is let through.
- FR-052 (record): a new `VerificationMiddleware` puts the server's **verification record** on the final reply (`additional_kwargs.omniharness_verification`, also kept in thread state `verifications` so it survives a reload and summarisation). It is built from this turn's tool results and checklist only (`agents/working_loop.py`): status `verified` only when every item is completed, a tool result backs the turn, there is no "Not verified" section and every link in the reply appeared in a tool result of the turn; `unverified` otherwise; `none` when there is nothing to verify. The chat shows it as the Verified/Unverified badge.
- FR-054: tool-error and loop-detector texts rewritten ("read the error, change something, do not repeat"; forced stops say "report the unfinished items as not verified"). Thresholds unchanged.
- FR-056: a trailing "Would you like me to…?" / options paragraph is removed from the final reply when enough of the reply stays to stand on its own (recorded as `style_fixes`); the policy layer's Tier 2 disclosure block is never touched.
- FR-057: `ask_clarification` accepts only `missing_info` and `ambiguous_requirement`; a question asked after work has started in the turn is sent back once with "pick a default, state it, continue, or stop as blocked" (a second one in the same turn goes to the person, for a task that truly became impossible).
- FR-058: #139's resume is widened to **every Tier 3 card the lead raised in a chat turn** (project/goal, delegation, deletion, skill/agent change, connector write, mixed with outbound cards): once no card of the turn is open, one resume run starts with each card's outcome as a tool result. A turn whose cards were all declined resumes too (the lead says what was not done). Delegate cards still use Continue <agent>; resuming the lead after a delegate's Continue is **not built** (follow-up).
- FR-058a: in a resume run, a call identical (tool + canonical arguments) to one the person declined in that turn is refused by the policy layer (a refusal only; it can never run anything).
- FR-059: summarisation writes a server-built **plan record** next to #141's turn summary: checklist, done-criteria, findings already verified (tool, query or URL, from the tool RESULTS so a call folded into an earlier summary still counts) and open blockers, and appends it to the summary text the model reads ("Already done and verified (do not repeat these calls)"). Findings of an earlier turn are never carried into a new one.
- FR-061: `research` tool and `research` subagent (above).
- Prompt: `<working_loop>` replaces `<clarification_system>` and the clarify-first rules; reads never ask (a memory note about confirming first never applies to reads); no tool-call narration; files go to outputs and are presented; no menus; bounded work; long tasks continue from the plan record.

**Two fixes the eval found**
- *Trusted checklist echo.* `write_todos`' result ("Updated todo list to […]") is composed from the call's own arguments. It was an untrusted tool result, so with the checklist now written first, every routine ledger write after it became a content-originated suggestion card (T10 would have regressed). It is now a trusted acknowledgement, marked by the identity of the registered function (never by name), like `ledger_apply`'s. Any untrusted result earlier in the turn still taints everything after it. **Owner review point** (lineage.TRUSTED_TOOL_RESULTS is an owner decision of 2026-10-20).
- *"database is locked" before a card.* Stating a ledger card checks the plan with a dry-run write transaction. On the run's event loop it waited for SQLite's write lock while the lock's holder (the run journal's async writer, same database) needed that loop to commit: the check timed out, fell back to proposing the plan unchecked, and an invalid plan reached a card and failed after the person confirmed it (the baseline's T11 `RuntimeError`). A card is now stated off the event loop (`_off_loop`).

**Per-run trace (FR-080 to FR-084)**: every lead run (chat, resume, scheduled) writes one run-history record of kind `chat` when it ends (`app/run_history/chat_trace.py`), through `RunHistory.record()` (redaction, encryption, caps, retention, Delete unchanged). Steps (checklist, tool, subagent, card, card_resolved, resume, retry, summary, verify, reply) carry type, name, tier, status, timing, parent and source event; statuses come from the run journal's events and the policy layer's stamp on each tool result (`omniharness_policy_step`), never from prose. Tokens by model and an estimated cost (list prices; unknown model → unknown cost). `GET /api/run-history/traces/{run_id}`, `GET /api/run-history/runs?kind=chat&thread_id=…`; a resume names the run it resumed (`resumed_from`) and a trace lists the runs that resumed it (`resumes`). Known gap: a call that raised before the policy layer could stamp it has no tier in the trace.

**UI**: the checklist in chat (any mode; "Done when" shown as the criteria line); the Verified/Unverified badge with its checks; Settings → Evals (score history, per-task pass/fail with check reasons, baseline column, live-only tag); the trace view. Graphite tokens, both themes, AA contrast checked in Playwright.

**Eval suite (FR-070 to FR-079)**: `make eval` (`backend/tests/eval/`): 20 T-tasks (the 18 of spec.md plus the owner's dogfooding tasks T19 "compare 3 Next.js auth libraries" and T20 "no narration, no menu, file presented") and 9 mock-only tasks (M-RETRY, M-SUMMARY, M-DECLINE, M-MIXED, M-VERIFY, M-MIDASK, M-MENU, M-FLASH, M-RESEARCH-PRIVATE). Every trial is a fresh gateway (`create_app()`), temp data dir and HOME, tracked config (example + `fixtures/overrides.yaml`), no channels/connectors/MCP, policy ON with the shipped rules, a throwaway owner, fixtures through the public API; calendar and mail are stubs under their real tool names. Mock mode: in-process, scripted model that fails on divergence, recorded web; runs in the backend unit-test job (`tests/eval/test_eval_mock.py`). Real mode: one uvicorn process per trial on a free port, the model key read from `EVAL_ENV_FILE` into that process only. Results go to `eval/results/` (gitignored) and feed Settings → Evals; the accepted baseline is `backend/tests/eval/baseline.json`. The owner's dogfooding cases map to: Philly date night → T01; Next.js auth → T19; read-only weekly calendar → T03; long research without a menu or re-searching → T07 (`no_repeat_calls`, `max_calls`); stop at a Tier 3 card and resume → T11; retry after an error → T13; no narration / no menu → linters on every task + T20; file in the panel → T15, T20.

Live-only: T03, T04 and T05 against the owner's REAL calendar and mail are not run by the eval (an isolated instance never reads real accounts); the suite runs them against the stubs, and the live versions are left to the orchestrator.

## AgentTrail (the coding-session evidence reference) and this slice

AgentTrail (open-source, MIT; cited in the owner's brief of 2026-10-19/20 as the reference for coding-session evidence) watches terminal coding agents' session logs: discovery, turn state, tool activity, subagent links, native todos, opt-in hooks for "waiting on you", declared-vs-observed drift. Already in OmniHarness: session_watcher (codex adapter, todo parsing confirmed by tool results), the run store (RunRow tokens/calls/status) and run_events journals (persisted since #155), the encrypted run history for automations (#55), the Activity log. Missing: opt-in hooks (so "waiting on you" is observed, not inferred), declared-vs-observed (the ledger's `declared_files` is unused), and a per-run trace view of chat runs. It is not the per-run trace of this assistant's lead; the owner asked for that view anyway, and Slice 0 builds it (above).
